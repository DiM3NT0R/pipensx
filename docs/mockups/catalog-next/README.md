# pipensx · следующий каталог

Интерактивный дизайн-концепт Web Companion и новой модели каталога.
Откройте `index.html` напрямую или запустите из корня проекта:

```sh
python3 -m http.server 8765 --bind 127.0.0.1 --directory docs/mockups/catalog-next
```

Затем откройте <http://127.0.0.1:8765>. Для открытия с телефона в той же сети
можно сменить адрес привязки на `0.0.0.0` и использовать локальный IP компьютера.
Это демонстрация интерфейса, не сервер управления настоящей консолью.

Скриншоты: `preview-desktop.png`, `preview-mobile.png`, `preview-install.png`
и `preview-studio.png`. Обложки находятся в `assets/`.

## Что попробовать

- Обзор → Hades → выбор версии и файлов → расчёт места → очередь.
- Поиск по названию, студии, жанру и описанию; фильтры языка и размера.
- Избранное и библиотека; обновление Dead Cells без повторной установки базы.
- Загрузки → «Демо: обрыв» → «Продолжить» → проверка сохранённых данных.
- «Демо: завершить» → установленная игра появляется в библиотеке.
- Перестановка очереди, пауза, очистка истории без удаления установленного.
- Источники → переключатели → настройки сохраняются в браузере.
- Catalog Studio → успешная демосборка; затем сборка с ошибкой проверки.
  Ошибка не меняет опубликованную версию.
- Мобильная компоновка, клавиша `/` для поиска, Escape для закрытия диалогов.

Установки, версии, размеры, совместимость, IP, скорость и CI — демоданные.
Ссылки на скачивание игр и настоящие ключи отсутствуют. Файлы не устанавливаются.
Состояние хранится в localStorage, если браузер разрешает это; иначе работает
до закрытия вкладки. Сброс доступен в Catalog Studio. При открытии по другому
origin или через `file://` состояние может храниться отдельно.

## Концепция независимого каталога

Нужен отдельный репозиторий, например `pipensx-catalog`, с нашей схемой,
адаптерами источников, редакционными исправлениями и проверками. Каталог
Langegen не должен быть обязательным upstream. Его можно поддержать как
необязательный пользовательский адаптер, если условия источника позволяют.

Разделить **метаданные игры**, **редакционные подборки**, **описания релизов**
и **доступность загрузки**. GitHub Actions собирает и проверяет метаданные,
а Switch проверяет конкретный способ загрузки. Успешный CI не означает наличие
живых пиров, кэша TorBox или совместимость на конкретной прошивке.

### Модель данных

```json
{
  "schema_version": 1,
  "game_id": "switch:example-stable-id",
  "platform": "switch",
  "title_id": null,
  "titles": { "en": "Example Homebrew", "ru": "Пример приложения" },
  "aliases": ["Alternative title"],
  "genres": ["puzzle"],
  "languages": { "text": ["en", "ru"], "voice": null },
  "releases": [
    {
      "release_id": "author:example-homebrew:v1.2.0",
      "version": "1.2.0",
      "kind": "homebrew",
      "components": ["application"],
      "installation": { "target": "switch/example", "format": "zip" },
      "sha256": null,
      "source_id": "official-author-release"
    }
  ],
  "provenance": {
    "titles.en": {
      "source_id": "official-author-release",
      "retrieved_at": "2026-09-30T07:17:00Z",
      "license": "requires-source-review"
    }
  }
}
```

Это пример схемы, не валидированный production-формат. Для пакетов Nintendo
модель включает base/patch/DLC и связи идентификаторов; NRO без title ID получает
стабильный ID внутри namespace автора. Info hash идентифицирует раздачу,
а не игру. Совпадения только по названию отправляются на review. Формат языка
нормализуется по кодам; «неизвестно» не превращается в «нет русского».
Версии пакетов сравниваются по структурированным значениям, когда они доступны,
а не только по строкам display_version.

### Откуда брать данные

1. **Homebrew**: разрешённый список официальных GitHub-репозиториев и их Releases.
   Инкрементальные запросы с ETag, rate limits и provenance. Метаданные релиза
   не доказывают наличие SHA-256: публиковать только полученный digest или
   проверенный хеш разрешённого asset. Отсутствующий хеш отмечать явно.
2. **Метаданные игр**: разрешённые источники с проверенными условиями использования,
   плюс собственные правки сообщества. Название, ID и языки хранить отдельно от
   обложек и описаний: у них могут быть разные ограничения распространения.
3. **Подборки и исправления**: JSON/YAML в репозитории, pull requests, проверки
   схемы и review. Начать с небольших качественных подборок, а не со скрейпинга
   максимального числа карточек.
4. **Личные релизы пользователя**: локальный импорт или настроенный HTTPS-источник.
   Они связываются с карточками на клиенте. Пользовательские magnet, credentials
   и приватные каталоги не попадают в публичный каталог и CI.

### Сборка на GitHub Actions

Предлагаемое расписание: `17 */6 * * *`, плюс `workflow_dispatch` и проверка PR.
Полный reconciliation — например раз в неделю; чаще обновляются только
изменившиеся источники. Не выполнять код из скачанных архивов. При PR проверять
только схему и фикстуры с read-only permissions, без publishing/signing secrets.
Публикацию делать отдельной задачей из доверенной default branch. Actions
закреплять по SHA; job permissions минимальные, concurrency предотвращает
параллельную смену latest.

Порядок:

1. Скачать разрешённые метаданные. Сохранить ETag, даты и последний валидный
   результат адаптера. При сетевом отказе источник пометить stale, а не пустым.
2. Нормализовать ID, названия, жанры, языки, версии и связи компонентов.
3. Проверить схему, уникальность, dangling references, provenance и лицензии.
   Нулевые записи, слишком большие дельты и массовые удаления блокируют
   публикацию. Удаления подтверждаются явными tombstones/reconciliation.
4. Детерминированно собрать индекс, отдельные языковые поля и карточки по shard.
   Выпустить дельту с `base_version`, `target_version` и удалениями.
5. Посчитать SHA-256 выходных файлов. Подписать manifest отдельным ключом;
   публичный ключ доверия должен быть встроен в клиент. Процедура ротации нужна
   до production. Ключ подписи хранится в protected environment/secret.
6. Опубликовать полный неизменяемый снимок. Затем поменять указатель latest.
   Клиент всё равно обязан проверить подпись и файлы, прежде чем заменить кэш.

Сервисам GitHub не нужно поручать скачивание игр или постоянный torrent health
monitoring: это другой объём нагрузки и не даёт достоверной оценки сети Switch.
Диагностика доступности источников и проверка реальной загрузки — разные статусы.

### Доставка без собственного сервера

- **GitHub Pages**: небольшой manifest, bootstrap-индекс, документация и при
  подходящем объёме sharded данные. У опубликованного сайта лимит 1 ГБ и мягкий
  лимит трафика 100 ГБ/месяц; хранить весь архив снимков и арт здесь не стоит.
- **GitHub Releases**: версионированные полные снимки и дельты. Workflow artifacts
  годятся для проверки, но не являются постоянным публичным каналом доставки.
- **Клиент Switch**: индекс для выбранного языка, lazy загрузка карточек,
  локальный кэш, дельты только для совпадающей базовой версии. После пропуска
  истории дельт — полный снимок. Кэш заменять атомарно после проверки.
- **История**: хранить ограниченное число полных снимков и дельт. Задать срок
  поддержки schema/client_version. URL доставки отделить от схемы, чтобы позже
  добавить зеркало без смены идентификаторов игр.

Нужен мониторинг возраста manifest, а не обещание точного cron. GitHub может
задерживать или пропускать scheduled jobs, а в публичном репозитории после
60 дней без активности scheduled workflow автоматически отключается.
Ручной запуск помогает восстановить обновления; последнее корректное состояние
позволяет клиенту работать при задержке. Это независимость от домашнего ПК,
но всё ещё зависимость от внешней платформы.

### Что делать первым

MVP: независимая схема → 2 адаптера разрешённых источников → проверяемые
поправки через PR → компактный снимок + manifest → клиентский импорт и
последний исправный кэш. Затем локализации, группировка компонентов, подпись
и безопасная production-публикация, дельты и более богатые подборки. До выпуска
канала обновлений подпись и проверки доверия обязательны. Сначала измерить
размер каталога, время сборки и число запросов: макет не доказывает стоимость
и производительность будущего pipeline.

## Источники и графика

- [GitHub Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions):
  standard hosted runners в публичных репозиториях бесплатны; другие классы
  runners и условия хранения нужно считать отдельно.
- [GitHub Pages limits](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits).
- [Troubleshooting workflows](https://docs.github.com/en/actions/how-tos/troubleshoot-workflows).
- [Disabling and enabling workflows](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/disable-and-enable-workflows).

Иллюстрации локально сохранены с публичного Steam CDN для визуального
прототипа: app IDs 1145360, 367520, 504230, 588650, 413150, 1244090, 553420, 2379780. Изображения принадлежат соответствующим правообладателям; это не
передача права на их распространение в production-каталоге. Перед публичной
публикацией продукта заменить их разрешёнными ассетами или согласовать права.
Steam artwork используется как иллюстрация, а не как точная Switch-обложка.
Manrope загружается из Google Fonts; при отсутствии сети используется системный
шрифт. Остальная демонстрация работает без внешних запросов.

## Проверка макета

Пройден браузерный smoke-check в Chromium через Playwright: поиск по студии,
фильтры и подборки, выбор состава релиза, защита от дубликатов, восстановление
после обрыва и перезапуска страницы, завершение установки, библиотека,
сохранение настройки источника, успешная и заблокированная публикации.
Семь экранов проверены на ширинах 1440, 1280, 768 и 390 px; горизонтального
переполнения и ошибок JavaScript не обнаружено. На телефоне проверены меню,
диалог установки и доступность кнопки в главном баннере.

Сборки Switch/PC не запускались: изменения ограничены отдельным веб-макетом
и документацией, исходный код приложения не менялся.
